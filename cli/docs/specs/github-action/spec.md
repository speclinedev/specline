# github action — the CI enforcement wrapper

## Intent

Build the **enforcement** surface: a GitHub Action that runs Specline on every
pull request touching `docs/`, and **blocks the merge** when the change
doesn't conform. This is how a team stays on-method without relying on
goodwill or on everyone having read the canon — you can't merge a
non-conforming change. It is a thin wrapper over the same engine and output
contract as the CLI and the MCP server; only the trigger (a PR) and the
reporting (PR annotations) differ. The workflow file it runs is what
`specline init` optionally generates (see `specline-init`).

**Appetite — one sitting.** The composite action, the PR-diff → `--changed`
wiring, the exit-code gate, and PR-annotation reporting.

## Goal

A pull request that breaks a spec's structure cannot merge — the check fails
with inline annotations; a conforming PR passes, with parity to the local CLI.

## Non-goals

- **No validation logic of its own.** Every rule lives in the engine; the
  action only invokes it and reports. If a check is wrong, it's wrong in the
  engine, not here.
- **No judgment, no meaning.** It enforces *structure* — never whether a spec
  is good, right-sized, or true. That stays at the human approve gate.
- **Never mutates the repo.** It is a gate, not a fixer — it reads, reports,
  and sets a status. Generation/regeneration is `init`/`sync`'s job.
- **Not GitHub-only in spirit.** The engine + vendored binary run in any CI;
  this spec is the GitHub adapter specifically.

## Behavior

1. **Trigger.** Runs on `pull_request` events; the composite action is a step
   in the consumer's own workflow (generated by `specline init`), which scopes
   the trigger to changes under `docs/**` and the canon pin.

2. **Diff → `--changed`/`--modified`.** The action's shell step (`cli/action.yml`)
   resolves the PR's base ref (preferring the fetched remote-tracking branch,
   falling back to `FETCH_HEAD` for a shallow checkout), then computes two
   sets with a two-dot `git diff` against that base: every path changed under
   `docs/**` (`--changed`), and the subset that is a modification, deletion,
   or rename — not a pure addition — under `docs/**` (`--modified`, for
   archive-immutability detection). Both are **inputs** to the engine, exactly
   as it requires: the action computes them from git, the engine never reads
   git itself.

3. **Invocation.** Runs `node src/action/main.ts <path> --changed <files>
   --modified <files> --now <iso>`, where `--now` is the workflow run's UTC
   date, so time-dependent checks (staleness) are reproducible. `src/action/main.ts`
   calls the same `run()` the CLI calls — one mode, no `--mode`/`--tier` flags
   — and renders each finding as a GitHub workflow command
   (`::error`/`::warning`/`::notice`) instead of the CLI's human/JSON text, so
   findings surface as inline PR annotations.

4. **Gate.** Exit `0` → the check passes (green). Exit nonzero (an error
   finding or an execution failure) →
   the check fails (red), blocking merge under branch protection. The action
   gates on the **exit code**, never on message text.

5. **Reporting.** Each annotation carries the rule's `file`, `line` (when
   present), `rule_id`, `message`, and `fix_hint`, so the author self-corrects
   from the annotation alone — without opening the canon. A one-line summary
   (errors/warnings/info counts) is also appended to the PR's check-run
   summary when `GITHUB_STEP_SUMMARY` is available.

6. **Distribution.** A **composite action in the `cli` subtree of this repo**
   (`speclinedev/specline/cli@vMAJOR.MINOR` — the moving tag tracks the canon's
   MAJOR.MINOR): GitHub checks the action's repo out alongside the consumer's,
   installs its own runtime dependency (`yaml`) via `npm ci`, and runs the
   bundled engine directly — no separate package and no npm publish needed for
   CI.

## Business rules

- The action **must** gate on the exit code and **must not** parse message
  text to decide pass/fail.
- The action **must not** write to the repository under test.
- The action **must** pass the PR diff as `--changed`/`--modified`; it
  **must not** ask the engine to read git.
- A green check **must** mean zero `error` findings for the changed set — the
  same answer the CLI and MCP would give on the same input.

## Critical files

- `cli/action.yml` — the composite action definition and the shell step that
  computes `--changed`/`--modified` from git.
- `cli/src/action/main.ts` — the entrypoint that calls the shared engine and
  renders GitHub workflow-command annotations.
- `cli/src/engine/run.ts` — the engine, output contract, and exit-code
  semantics this wraps. Any divergence in pass/fail is a bug here, not in the
  engine.
- `specline-init` — generates the `.github/workflows/specline.yml` that
  invokes this action.

## Acceptance checks

- A PR that introduces a structural error to a spec it touches makes the
  check fail (red), blocking merge.
- A PR touching only spec A does **not** fail on a pre-existing spec-scoped
  error in spec B (quarantine); a repo-scoped error (e.g. duplicate slug)
  fails any PR.
- The check's pass/fail matches `specline check --changed <same files>
  --modified <same files>` run locally on the same commit (parity across
  adapters).
- Findings surface as PR annotations carrying `rule_id`, `message`, and
  `fix_hint`.
- A shallow (depth-1) checkout with no local base-branch ref still resolves a
  usable diff (via `FETCH_HEAD`) rather than erroring the gate.

### human

- `jonathan` confirms a contributor could correct a failing PR from the
  annotations alone, without reading the canon.

## Out of scope / deferred

- **The orchestrator / build loop** — the agents that shape and build
  (Part 3, experimental). The action is a gate they pass through, not a
  participant.
- **Auto-fix in CI** — regeneration is `init`/`sync`'s job, not the gate's.
- **Non-GitHub CI adapters** — the vendored-binary path works anywhere; other
  CI wrappers are their own specs.

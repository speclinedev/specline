# Canon v3.1 — amendment proposal (ratified)

**Status:** RATIFIED — folded into canon 3.1.0 (release `v3.1.0`, 2026-09-30).
Kept as the decision record; the canon (`specline-3.1.md`) is the law. This
document preserves the amendment rationale and proposed changes; the
implementation landed on `chore/principal-repo-review` (#26).

Shaped 2026-09-27 from a review of the
`chore/principal-repo-review` branch, where an "audit remediation" spent most
of its effort — and produced most of its regressions — on the unattended-build
machinery, while rewriting canon prose to match the validator. That review
surfaced a structural problem the branch was a symptom of; this proposal is
about the structure, not the branch.

**Posture.** This completes what v3.0 started. The v3.0 amendment diagnosed
*"two products fused in one canon"* and fixed the reading order; it left the
model intact. v3.1 finishes the separation: two normative parts — *writing a
spec* and *keeping the record* — plus one **opt-in** part, *unattended
builds*, in force only when a repo turns it on. Ceremony that leaked from the
third part into the first two is removed. Nothing is deleted from the
methodology. Every v3.0 spec stays valid and produces the same findings.

---

## In plain terms (read this first)

Specline is, first and before anything else, **a consistent way to write a
feature spec, and a consistent place to keep it** — beside the code, so a
person or an agent opening the repo can hydrate on intent: what is being built,
why, what was decided before, what is still open, and what already shipped.
That is the product. It replaces four ways of writing Linear tickets or GitHub
issues with one, and it puts the "why" in the one place every agent already
reads.

The canon does not read that way. The seven Boundaries open with "these seven
rules are the system," and four of the seven are about running a parallel agent
workforce. Eleven frontmatter keys, six of them a routing envelope. A status
enum with two states that exist only for an orchestrator. Acceptance checks
partitioned by *which agent role certifies them*, with names the decider does
not recognise. Six canon versions from v2.3 to v3.0, every one driven by
autonomous-agent concerns.

Nobody runs that machinery. It was designed around a bet — that models need
context rationed, mechanics withheld, and a six-section memory file to build
unattended — that has not been measured and may have aged. It is ambitious and
worth keeping. It is not law, and it should stop shaping the parts that are.

What this amendment does:

1. **Two normative parts.** Part 1, *Writing a spec*, is readable in one
   sitting and never mentions an agent. Part 2, *Keeping the record*, is the
   folder system and the only part the validator blocks on.
2. **Unattended builds become opt-in.** One switch — `unattended: true` in
   `specline.yml`, default off. When off, its rules are not listed, its keys
   are recognised silently, its chapter is not injected, and every surface
   labels it **experimental**. When on, it is a real, testable contract.
3. **Tiers are removed.** One system. The validator checks what is present;
   `unattended` is the only switch.
4. **Approval is a folder move; the lifecycle is location.** A spec being
   shaped lives in `docs/drafts/`; moving it to `docs/specs/` is the decider's
   go, recorded by git. The frontmatter `status` field is retired from `drafts/`
   and `specs/` and survives only in `archive/` (`shipped | killed`). The
   sequence — shape, approve, build, graduate — is not prescribed: one commit
   or many branches; Specline reads folders, not order.
5. **Acceptance is one list of falsifiable checks.** The three altitudes stop
   being required vocabulary. An optional marker says which items only a person
   can settle.
6. **The Boundaries shrink to what governs writing and record-keeping.** Three
   writing rules, one record rule. The rest move to the opt-in part.
7. **Contradictions are removed** — author/gate mode, slug-uniqueness wording,
   tier-gated integrity, the `stale_after` trigger — and the canon gets a
   versioning policy so a contract change cannot ship as a patch again.

## Diagnosis: three layers, one canon

The canon as written serves three distinct needs. Mapping it against them:

| Surface | 1 · The spec | 2 · The record | 3 · Operating unattended agents |
|---|---|---|---|
| **Boundaries** ("the system") | B1 One-Sitting, B6 Intent over description | — | B2 coupling ceiling, B3 human gate, B4 staleness, B7 decider budget; B5's three altitudes |
| **Frontmatter** (11 keys) | `slug type status decider created` | — | `build blast_radius size target_model stale_after loop_budget` |
| **`status` enum** | `draft building shipped killed` | (`ratified`) | `blocked` |
| **Spec folder** | `spec.md` + optionals | `relations.md`, `open-questions.md` | `status.md` |
| **Canon length** | ~150 lines | ~250 lines | ~450 lines |
| **Rule catalog** (34) | 9 | 12 | 13 |
| **Amendments v2.3 → v3.0** | — | — | all six |

Two patterns follow from the table.

**Layer 3 justifies layer-1 elements in its own terms.** `Goal` is a good idea
for any spec — one falsifiable sentence that means done — and the canon
explains it as "the one statement an autonomous run converges toward."
`Non-goals` is explained as fencing off over-building by strong models. The
writing rules are sound; their rationale and naming belong to the layer that
arrived last, so a reader cannot learn how to write a spec without being told
why an agent loop needs it.

**The tiers were a proxy for this segmentation, and a bad one.** Tier 0 = one
spec, tier 1 = the lifecycle, tier 2 = governance — nearly layers 1/2/3, but
gating which *rules fire* rather than which vocabulary, keys, states, or
chapters apply. On `main`, every integrity rule was gated to tier 1, so a
tier-0 repo — "one validated contract" — validated nothing. Tiers 0 and 1
differ only in whether `knowledge/` and `archive/` exist, and the record's
rules only fire on folders that exist. The distinction carries no value; the
switch that does is *unattended or not*.

Two things that look like layer 3 are not. **Graduation and archive are the
heart of layer 2** — "the why's of the past" *is* `knowledge/` + `archive/`.
What belongs to layer 3 is the mechanics: the agent-executed prompt wired to the
PR, carrying `## Corrections` forward, the promotion substrate. **Ratification
as "the decider's go, recorded as a commit" is layer 2** — a record of a
decision. What belongs to layer 3 is the ceremony that accreted around it:
checks frozen at ratification, an envelope set at ratification, B3 as a
Boundary. And one layer-3 import genuinely improved layer 1: *falsifiable
acceptance, settleable the same way twice* is a writing rule any product owner
should follow. It stays in Part 1.

## Part 1 — Writing a spec

A `spec.md` with five frontmatter keys — `slug`, `type`, `status`, `decider`,
`created` — and the body sections as today: Intent, Goal, Non-goals, Behavior,
Business rules, Assumptions, Critical files, Acceptance checks, Out of scope.
Body text unchanged except where it cites agents, loops, or envelopes; those
sentences are rewritten in human terms or moved to Part 3.

Three writing rules, restated without the operating rationale:

- **One sitting.** The contract is readable and judgeable in a single review
  sitting. If not, split it or decompose it (parent-map).
- **Falsifiable or draft.** Every acceptance check is settleable the same way
  twice. "Improve the dashboard" names nothing anyone can settle. Items only a
  person can settle are marked as such (see *Acceptance* below).
- **Intent over description.** The spec records what code cannot say — goals,
  non-goals, rejected options, rules, boundaries. Once code exists it owns the
  mechanics; prescribed mechanics compete with it and go stale.

**State is location.** Frontmatter is four keys — `slug`, `type`, `decider`,
`created` — and carries no `status`: a spec in `drafts/` is being shaped, in
`specs/` it is approved for build, in `knowledge/` it shipped, in `archive/` it
is the contract as built. Only `archive/` keeps `status: shipped | killed`,
because location cannot tell the two apart there. Existing `status:` lines are
recognised silently. There is no loop diagram: how a spec moves between folders
— one commit or several, one branch or many — is the repo's own workflow, and
Specline reads folders, not order.

**`docs/drafts/`** is the fourth lifecycle folder, same anatomy as a spec. Only
parse-level integrity runs there (frontmatter parses, slug matches folder, links
and edges resolve, slug not already taken); no advisory rule fires — incomplete
is what a draft is for. A draft may be deleted outright (nothing may depend on
it); one rejected for a reason worth keeping may be archived as `killed`.
`upgrade` moves any `specs/` entry still carrying `status: draft` or
`status: ratified` into `drafts/` so it does not silently become approved. Part 3's build state
(`building | blocked`) lives in `status.md`'s `## State` token, never in
frontmatter.

**Acceptance checks** are one list. The `### agent-loopable` / `### judgeable`
/ `### human-gate` partitions are no longer required or recognised as a
convention in Part 1. One optional marker survives because it helps whoever is
reading: an item only a person can settle sits under a `### human` sub-heading
(decided; `### human-gate` in existing specs is recognised silently). The
`— run:` entry shape
stays legal and unremarked (it is harmless; a runner may read it).

`Goal` stays: one line, the best single hydration hook a reader gets. Its
rationale is rewritten: *the one sentence that tells a reader whether the work
is done.*

## Part 2 — Keeping the record

Unchanged in substance; this is the part that works. Restated so it stands on
Part 1 alone:

- `docs/drafts/<slug>/` is being shaped; `docs/specs/<slug>/` is approved for
  build; `docs/knowledge/<slug>/` is what shipped, descriptive and permanent;
  `docs/archive/<slug>/` is the contract as built, verbatim and read-only. Slugs are chosen locally, are the identity,
  and are never reused for a different feature. The same slug in `knowledge/`
  and `archive/` is the normal end state, not a collision.
- `relations.md`: forward edges, each with a one-line *why*. `open-questions.md`:
  who decides, the options, the default, the deadline.
- When something ships, a knowledge doc lands and the spec is archived. When it
  is killed, it is archived with a one-line tombstone. Nothing is deleted.
- The record rule: **never delete a decision.** Slugs are permanent; archive is
  immutable. This is the one Boundary that survives from B2/B3/B4/B7's group,
  and it is the reason the integrity rules exist.

Graduation's *outcome* lives here. Its *mechanics* — the agent-executed prompt,
`## Corrections` carried into the knowledge doc, promotion — move to Part 3.

**Enforcement.** *Gate integrity, advise on taste* stays the law and is stated
once, here. The validator blocks only on: a `specs/` folder without `spec.md`,
unparseable frontmatter or `relations.md`, a slug that mismatches its folder,
an out-of-set enum, a dangling reference, a slug collision, a `status.md` in
`knowledge/`, an edit to `archive/`. Everything else warns. Unknown keys and
sections are preserved and warned. One mode; exit code is nonzero on errors.
Integrity always runs — there is no tier that switches it off. Quarantine in
CI: a spec's own errors fail a PR only when the PR touched that spec.

## Part 3 — Unattended builds (experimental, opt-in)

The current *Unattended builds* chapter, the runner contract, the build loop,
routing, agent-execution notes, promotion, `status.md` schema, staleness,
decider budget, coupling ceiling, and frozen checks — text preserved, gathered
here, and headed:

> **Experimental — in force only when `specline.yml` sets `unattended: true`.**

**The one switch.** Today three knobs partially gate this material: `tier`,
per-spec `build: unattended`, and the never-implemented `--mode`. After this
amendment:

- `unattended: true` in `specline.yml` enables the machinery for the repo.
  Default `false`.
- `build: unattended` in a spec's frontmatter stays as the per-spec declaration
  inside an enabled repo — different scope (repo capability vs. this spec's
  posture), and it already exists.
- `tier` is removed. `specline upgrade` maps `tier: 2` → `unattended: true`
  and drops `tier: 0|1`.
- `--mode` is deleted.

**What adapts when the flag is off** (everyone today):

| Surface | Off | On |
|---|---|---|
| `specline rules` | Parts 1–2 only. Part-3 rules are **not listed**, so an agent reading the catalog never learns they exist. | Full catalog; Part-3 rules tagged `experimental`. |
| `specline spec` (prompt-injected canon) | Parts 1–2. | Parts 1–2 + Part 3. |
| Envelope keys, `blocked`, `status.md`, acceptance partitions | Recognised silently, never warned. A repo that flips the flag off does not suddenly error. | Checked. |
| `init` / `sync` scaffold | Templates and folder READMEs omit envelope keys and `status.md`; `specline.yml` carries `# unattended: false  # experimental`. | Includes them. |
| MCP `build` prompt, planner prompt | Attended register only. | Adds the unattended brief. |
| Site | Unattended/runner pages carry an **Experimental** banner; rules page marks Part-3 rules. | Same banner (the site is static). |

The canon injected into every agent's context shrinks by roughly a third for
every repo not running autonomous builds. That is the token-efficiency goal
Part 3 was chasing, delivered by removing Part 3 from the prompt. Cost: one
section marker in the canon file and a slice in the CLI.

## Contradictions removed

Found by the review; fixed here regardless of anything else in the proposal.

1. **Author mode / gate mode.** §Enforcement says author mode is advisory and
   exits clean; the v3.0 changelog (#24) says the engine retired that
   downgrade; the body governs, so the canon promises it — and the code never
   implemented it (`--mode` is inert on every version). Gate mode's "lifecycle
   requirements are now errors" also contradicts *gate integrity, advise on
   taste*. Resolution: one mode. The distinction was a pre-v2.6 leftover.
2. **Slug uniqueness.** "Repo-unique across `specs/ ∪ knowledge/ ∪ archive/`"
   next to "carried unchanged through graduation into `knowledge/` and
   `archive/`." Resolution: unique per feature; the graduation pair is the
   normal end state. The engine on `main` also compared only `specs ∪ archive`
   — under-enforcing; the review branch's fix toward the canon is correct.
3. **Tier-gated integrity.** "Tier 0 — run Specline. Value: one validated
   contract" — but every integrity rule on `main` was gated to tier 1.
   Resolution: tiers are removed and integrity always runs. (The review
   branch's code fix — integrity at tier 0 — is the same behaviour and
   survives; only the `tier` concept goes.)
4. **`stale_after` trigger.** B4 and the frontmatter comment say `building`
   *and* `blocked`; the Checks appendix said "once building." Resolution:
   building or blocked, as the body already said.
5. **No versioning policy.** The canon has never defined PATCH / MINOR /
   MAJOR; that is how a contract change shipped as 3.0.1. Resolution, added to
   the canon header, consistent with how every prior bump was actually
   justified: *PATCH — prose only; no rule, key, state, or severity changes.
   MINOR — every spec valid under X.Y stays valid; no previously-clean repo
   gains an integrity error. Catching invalidity that was already there (a
   file that never parsed) is a fix, not a break. MAJOR — a valid spec can
   become invalid.* Under that policy this amendment is a MINOR, and the
   review branch's 3.0.1 should have been one too.

## Tooling delta

Engine and CLI changes this amendment requires, kept deliberately small:

- `specline.yml`: new key `unattended: boolean` (default false). `tier` is
  accepted and mapped for one MINOR (warn `UNKNOWN-CONFIG-KEY`-style, no
  error); `upgrade` rewrites `tier: 2` → `unattended: true` and drops
  `tier: 0|1`.
- Rule registry: each rule carries `part: 1 | 2 | 3`; the `tier` field goes.
  Part 3 runs and is listed only when the flag is on; listed rules carry
  `experimental: true`.
- Enum handling: `status: ratified|blocked`, envelope keys, and the acceptance
  partition headings are recognised silently when the flag is off (no
  `UNKNOWN-*` warning, no check). `ratified` is treated as `building` for any
  rule that reads status.
- `--mode` and `--tier` removed from CLI, MCP, and the Action. `downgradable`
  removed from the registry and from `specline rules` output.
- `specline spec` slices the canon at the Part 3 marker when the flag is off.
- Scaffold: `init` writes Part-1/2 templates; adds the commented
  `unattended` line to `specline.yml`; folder READMEs regenerate from the
  re-segmented canon.
- Site: Experimental banner component on the unattended/runner/build-loop
  pages; rules page groups by part; the tiered adoption page is replaced by
  "adopt the spec, then the record; flip the switch if you run unattended."

Not in scope: the GitHub Action's change-base logic (five regressions on the
review branch — a separate rework), `Specline diff`, `relations-index`
generation, `target_model` resolution (all still *planned*, and all Part 3).

## Migration — MINOR, no broken specs

- A v3.0 spec is a valid v3.1 spec. Envelope keys, `ratified`, `blocked`, and
  partition headings are recognised silently when `unattended` is off, so no
  new warnings fire on existing repos.
- `specline upgrade` rewrites the `specline.yml` pin, maps or drops `tier`,
  and regenerates folder READMEs. It also relocates each entire
  `docs/specs/<slug>/` folder with `status: draft` or `status: ratified` to
  `docs/drafts/<slug>/`. Authored file contents, including the old status
  field, are preserved; their paths change. `status: building` and status-free
  spec folders stay in place. Authored entries in `knowledge/` and `archive/`
  are not moved or rewritten.
- Adoption is therefore not necessarily a pin-only change: each legacy draft
  requires a folder move. Run `specline upgrade PATH --check` with the
  3.1 CLI in a disposable copy first; it lists planned moves without writing
  (exit 1 means changes are needed). Review the actual upgrade diff there,
  including any consumers of hard-coded paths, before applying it to the repo.
  Editing the pin alone does not run this migration; in 3.1, leaving a draft
  in `docs/specs/` makes its location communicate approval.
- Repos that *do* run the unattended machinery set `unattended: true` and see
  the same rules they had at tier 2, now labelled experimental.
- `RELATION-UNPARSEABLE` now fires on a malformed `relations.md` that
  previously produced nothing. That file was never valid; this is the
  validator catching up, and under the policy above it is a fix, not a break.

## Decisions (decided 2026-09-27)

0. **`docs/drafts/` is the fourth lifecycle folder; approval is the move to
   `specs/`; the frontmatter `status` field is dropped except in `archive/`;
   the loop diagram is removed from the canon.** The sequence varies per repo
   and per spec; the folders are the contract.

1. **The human marker on acceptance items — `### human` sub-heading.** The
   one partition that was always real, and a heading is what the parser
   already finds. `### human-gate` in existing specs is recognised silently.
2. **`decider` stays as the key name.** Renaming churns every existing spec
   for no functional gain.
3. **`GOAL-MISSING` stays as an advisory warning.** One line, highest
   hydration value per character in the format.

## Cost, honestly

- **Canon edit**: large in diff, small in substance — mostly moving text under
  new headings and deleting ~80 lines of ceremony and the tier material. One
  sitting to review if read as a before/after map, not a diff.
- **Engine**: a `part` field replacing `tier` on 34 registry entries, one
  config key, one slice in `spec`, deletion of `--mode`/`--tier`/
  `downgradable`, enum tolerance for the off state. Days, not weeks. Every
  commit independently testable.
- **Hand-maintained mirrors** (per `CLAUDE.md`): README, handbook (both
  surfaces), site reference pages, `cli/README.md`, the doctor spec. This is
  the expensive part and the part most likely to drift — the review branch
  proved it. Do it once, after the canon text is final, as its own commit.
- **The review branch**: its Parts-1/2 engineering fixes (parser correctness,
  slug integrity, integrity-always-on, 64 KiB output truncation, CLI/MCP
  validation, upgrade pin preservation, typecheck, site) are kept and
  cherry-picked first. Its canon/spec prose edits are dropped — superseded by
  this document. Its Part-3 rule tightening is moot behind the flag. Its
  Action rewrite is reworked separately.
- **What we lose**: nothing functional. Part 3 is one config line away for
  anyone who wants it. What we give up is the claim that the seven Boundaries
  are the system. They were the system for an orchestrator this repo never
  built; the system that exists is a way to write specs and keep the record.

# Canon v3.0 — amendment proposal (revised after review, for ratification)

**Status:** RATIFIED — folded into canon 3.0.0. Kept as the decision record;
the canon (`specline-3.0.md`) is the law. Shaped 2026-09-05 from a run: the
decider authoring specs for an attended builder and finding the builder
combative. Revised the same day after two independent fresh-context reviews
(one Opus, one Sonnet, identical briefs, neither shown the author's
conclusions). Per `docs/research/findings.md`: decide from runs, not theory.

**Posture.** The spec body does not change. The canon changes what it assumes
about who is building, what it tells the builder, and what it requires of the
branch. Every v2.8 spec stays valid. Nothing is deleted from the methodology;
the parts written for a runner stop being the default reading and stop being
required of a build that is not one.

---

## In plain terms (read this first)

Specline has two products fused in one canon. The first is the spec
discipline: one folder shape, intent and non-goals, a checkable definition of
done, open questions with a default, graduation into permanent knowledge. The
second is a runner contract: loop budgets, staleness, frozen checks, a
six-section status file with machine tokens, blast-radius routing, decider
budgets. The second was designed for an orchestrator this repo has never
built, and today every agent that reads the canon loads all of it and reads it
as rules of engagement with the human.

The canon's founding sentence says the builder is "a different agent, never in
the room, unable to ask what you meant." In the run that produced this proposal
the builder was in the room, and asked. The decider's actual workflow is one
branch: write the spec, build against it in the same branch, graduate it, open
one pull request. The canon currently describes a different workflow as the
rule.

Both reviews found the same thing: the engine already enforces almost none of
the autonomous machinery on such a spec. It emits two advisory warnings. The
weight the decider feels is prose the builder reads with no persona, plus a
canon that still instructs agents to set a ratification field it abolished in
v2.6. Fix those and most of the friction goes.

What this amendment does:

1. **A spec is attended unless it says otherwise.** One optional key marks a
   spec as unattended. Absence means attended. The key is a declaration the
   format carries, so nobody has to be asked, and it is the promise that a
   builder who cannot ask has everything it needs.
2. **Merge-first is not a rule.** No spec has to land on the merge target
   before work begins. One branch may carry shaping, building, and graduation,
   and the approving merge of that branch is the record.
3. **Amendment is a normal move.** An attended builder disagrees out loud,
   edits the spec in the branch once the decider agrees, and the diff is the
   record. The handback ceremony stays for unattended builds only.
4. **The builder gets a brief.** A `build` prompt in the register of the
   planner persona.
5. **The canon reads attended-first.** The attended spec is described as the
   whole thing; the runner material becomes one later chapter.
6. **Contradictions are removed.** The `ratified_by`/`ratified_at`
   instructions, and the `distance_to_ratifiable` prose for a feature the
   engine retired.

What this amendment deliberately defers, on the reviewers' evidence: gating
rule severities by the key, serving half the canon from the spec tool, and any
new runner MUST-items. Each needs a runner or a diff tool this repo does not
have.

## Build posture: `build: attended | unattended`

**Change.** One new optional frontmatter key on `spec.md`:

```yaml
build: unattended     # OPTIONAL. attended | unattended. Absent means attended.
```

It names the one variable that decides whether the autonomous machinery is
load-bearing: **can the builder reach the decider during the build.**

- **attended** (default, and the meaning of absence). A human, or an agent with
  the decider reachable, builds. Nothing in the unattended chapter is required.
  Mechanics stay sparse because the builder can ask.
- **unattended.** A fresh-context agent builds alone and the decider sees the
  result at QA. Marking a spec unattended is a promise: the builder has
  everything it needs without asking. The unattended chapter applies.

**Why absence means attended.** The decider does not reliably go through the
shape prompt; specs are drafted by an agent after a long conversation, from
the canon as read. A mechanism that depends on a question being asked does not
reach that path. The format has to carry the decision, and the cheap posture
is the default.

**The key is a declaration, not a switch.** Reviewers objected, correctly,
that letting the key change which rules fire would break the rule catalog's
self-describing property: `specline rules` could no longer say what a spec is
graded against. So the key changes nothing about rule severity. Every advisory
rule that fires today keeps firing. The key does three things: it is checked as
an enum, it drives one new advisory rule (below), and it tells a builder or a
runner which chapter of the canon and which brief applies.

**Set at shaping, confirmed at ratify.** The planner asks it early in product
terms. It can change later, because it is additive.

**The body does not fork.** Intent, Goal, Non-goals, Behavior, Business rules,
Assumptions, Critical files, Acceptance checks, Out of scope are identical in
both postures. Only the envelope fields and the builder's posture differ. One
reviewer noted that *required completeness* still scales with posture, per B6;
that is true and intended, and it is already how the planner persona behaves.

**New rule.** `UNATTENDED-INCOMPLETE` (advisory): `build: unattended` and any
of `blast_radius`, `loop_budget`, or (once building) `stale_after` is absent,
or `status.md` is absent. This is the report the author sees the moment they
set the key.

## Merge-first falls away

**Change.** v2.8 says "Merge to main is the ratification event" and, in B3, "a
spec no human approved into the main tree did not need to exist." v3.0
removes the requirement that a spec land on the merge target before work
begins, for every spec.

- **Ratification is the decider's go, recorded in git.** In practice the
  commit that flips `status` to `building`, made or approved by the decider,
  on whichever branch the work is happening. Git still owns who and when. B3
  becomes: "a spec no human approved did not need to exist."
- **One branch is the normal shape.** Shape, build, graduate, one pull request.
  Graduation was already "wired to the implementation PR"; it now lands in the
  same branch as the spec it graduates. The approving merge of that branch is
  the single durable record of contract, build, and graduation.
- **A spec PR ahead of the build stays legal** and is the natural shape when
  shaping runs well ahead of building or when parallel shaping is heavy and a
  slug needs claiming early. It is no longer the rule.
- **Slug freeze decouples from ratification.** A slug is immutable once it
  lands on the merge target, because from then on other work can reference it.
  Before that, re-slugging is legal, exactly as today. The word "ratified" is
  removed from the freeze rule; the mechanism (dangling inbound edges,
  archive edits) is unchanged.

**What the merge was doing for an unattended run, honestly.** Both reviews
made the same point: for a runner, the merge was a third-party-witnessed
baseline the implementer could not alter, and the tamper check came free from
diffing against the merge target. The working-tree engine cannot read git, and
`Specline diff` is still planned, so any replacement the canon prescribed
would be unverifiable here. The canon therefore **names the concern and leaves
the mechanism to the runner**, consistent with its existing rule that runner
mechanics belong in the runner's own contract doc: *a runner that needs a
frozen baseline for the checks it executes declares how it obtains one, for
example by requiring the spec merged before it starts, or by pinning the
spec's commit at start and diffing against it.* The canon requires neither.
This is a runner-contract SHOULD, not a MUST.

**Failure mode.** A runner that declares no baseline can be gamed by the
implementer weakening a check. That risk exists today for any spec built
without a runner; the amendment does not widen it for attended work and moves
the obligation to the only actor that can discharge it.

## Amendment is a normal move, attended

**Change.** Lifecycle, *Amendment (reshape) mechanics*, splits by posture.

- **Attended.** The builder finds a contradiction or a better cut, says so in
  product terms, and the decider agrees or not in the conversation. On
  agreement the builder edits `spec.md` in the branch. Acceptance checks are
  part of the contract: the builder proposes a change to a check before
  changing it, never silently. The diff is the record; the approving merge
  ratifies the amended contract with the code. No status flip, no separate
  PR, no re-ratification ceremony.
- **Unattended.** Unchanged from v2.8: flip to `blocked`, spec-amendment
  commit approved by the decider, resume. This is a handback because there is
  no conversation to have.

**Why.** v2.8's own instrumentation expects a mid-build revision rate of
10–40% and then models the normal path as a failure path. The builder in the
run behaved as if in a handback when it was in a conversation.

## The builder brief

**Change.** A second MCP prompt, `build`, served from `cli/prompts/builder.md`,
in the register of the v0.3 planner persona. Its posture:

> You are building from a spec a product owner wrote or co-wrote. Read the
> whole folder. Audit it against the code before you write any: what it gets
> wrong, what it leaves out, what would be cheaper another way. Disagree out
> loud, in product terms. When the owner agrees, edit the spec in this branch;
> the diff is the record. Acceptance checks are the contract's definition of
> done: propose a change to one before you change it, never silently. Then
> build, and ground every claim of done in a tool result.

When the spec carries `build: unattended` the brief tells the builder to read
the Unattended chapter and hold the v2.8 posture: frozen checks, status
memory, escalate at a boundary.

`docs/conventions/specline-CLAUDE.md` gains one line: *a spec is attended
unless it says otherwise; marking it unattended means you are promising a
builder that cannot ask you anything has everything it needs.* It loses the
`ratified_by`/`ratified_at` instruction and the `distance_to_ratifiable`
sentence.

**Why.** The combative feel traced to three causes: no builder brief,
amendment modeled as an exception, and contradictory ratification
instructions. Both reviews agreed the brief and the contradiction removal do
most of the work, and that this is the first thing to ship.

## The canon reads attended-first

**Change.** The canon is reordered. The attended spec is described as the
whole thing: What this is, the Boundaries that stand without a runner (B1
One-Sitting, B3 Human Gate, B5 Falsifiable, B6 Intent), Roles, Repository
layout, IDs, Spec folder anatomy, the body, `open-questions.md`,
`relations.md`, Decomposition, Selective loading, Lifecycle, Enforcement,
Adoption. Then one chapter, **Unattended builds**, holding the remaining
Boundaries (B2, B4, B7 as they apply to parallel runners), the `status.md`
schema, Promotion, the build loop, Routing, Agent-execution notes, and the
runner contract. Sections move; their text does not change.

The founding sentence changes. v2.8: "You shape a feature with one agent, and
a different agent builds it — fresh context, never in the room, unable to ask
what you meant." v3.0: "A spec carries the decision so that whoever builds it,
a person, an agent beside you, or an agent alone overnight, builds what you
meant. A spec is attended unless it says otherwise; marking it unattended is a
promise that a builder who cannot ask has everything it needs."

**`specline_spec` keeps serving the whole canon.** Reviewers found there is
no chapter boundary the parser can split on, and that the tail sections sit
after where the split would go. A split argument is deferred (below). The
reorder alone puts the default first for an agent reading from the top or from
memory.

## Contradictions removed

- Every remaining instruction to set `ratified_by`/`ratified_at`: canon
  Lifecycle two-PR text, amendment mechanics, the `Specline diff` description,
  the mid-build revision instrument, and the agent brief. v2.6 already made the
  merge the record; the prose never caught up.
- The `distance_to_ratifiable` sentence in the agent brief and the site
  lifecycle page. The engine retired author-mode downgrade; author and gate
  modes now differ only in name.
- The site's `llms.txt` text "ratify by merging to main."

## Deferred, and what would un-defer each

| Deferred | Why | Precondition |
|---|---|---|
| Gating rule severity by `build:` | breaks the self-describing rule catalog; needs a posture field on rule metadata and a folder lookup in the runner loop that do not exist | a second run showing advisory noise, not tone, is the remaining problem |
| `specline_spec` serving the attended canon only | no parseable chapter boundary; moves the "will the agent ask for the rest" failure down a level | sentinel markers carried by `sync-canon`, and a run showing the canon's length is itself degrading output |
| Runner MUST: refuse an unattended build without the key | unenforceable here; would force a mass edit on the one external runner known to exist (git-treeline) | a runner in this repo that implements and tests it |
| Runner MUST: pin the spec's commit at build start | the engine cannot read git; `Specline diff` is planned, not built | `Specline diff` shipped |
| Redefining `tier` in terms of the key | do not add a third knob before the second is used | a run |

## Tooling delta

Everything below is gated on ratification; none of it is built yet.

**Engine (`cli/src/engine/rules.ts`).** Add `build` to the known frontmatter
keys and an allowed-values set to the enum checks, so a bad value is
`ENUM-INVALID` and a good one is not `UNKNOWN-FRONTMATTER-KEY`. Add
`UNATTENDED-INCOMPLETE` to the registry and the rule list, advisory, spec
scoped, tier 1. Tests for both. No change to `schema.ts`, `model.ts`, or
`run.ts`: the report shape and the gating loop are unchanged because severity
is not partitioned.

**MCP (`cli/src/mcp/index.ts`).** Add a `build` entry to the prompt list and
replace the hardcoded single-prompt branch with a name-to-file map. Add
`cli/prompts/builder.md`. Prompt files are read from disk, not embedded like
the canon; note this for any future compiled MCP. No change to `specline_spec`.

**Scaffolder and consuming-repo CI.** No code change. The scaffolded workflow
pins the moving `@v${MAJOR.MINOR}` tag, so on release the `@v3.0` tag must be
created or every consuming repo's Actions run fails on a missing ref. This is
the largest operational risk in the release and was absent from the first
draft. `specline upgrade` rewrites only the pin in `specline.yml`; a repo left
on `@v2.8` grades 3.0 specs with 2.8 rules, which is noisy (`UNKNOWN-FRONTMATTER-KEY`
on `build`, `CANON-PIN-MISMATCH`) but never blocking.

**This repo's workflows.** No edits. `cli.yml` and `deploy.yml` glob
`specline-*.md`; `release.yml` greps generic strings.

**Release checklist, per `CLAUDE.md`.** Rename to `specline-3.0.md`; run
`sync-canon` to regenerate the bundle and the embedded copy; reconcile the
README canon line, the site `/docs/reference/*` pages (lifecycle, frontmatter,
rules, boundaries), both handbook surfaces, and `llms.txt`; restart the live
MCP process and confirm `specline_rules` reports the new canon; cut the
release and move the `@v3.0` tag. `CLAUDE.md`'s hand-maintained mirror list
gains `cli/prompts/*`, `docs/conventions/specline-CLAUDE.md`, and
`site/src/pages/llms.txt.ts`.

## Migration — non-breaking

- A v2.8 spec without `build:` is attended. Its envelope fields are preserved
  and checked exactly as today. It validates with the same findings.
- A v2.8 spec being built by an external runner adds `build: unattended` when
  convenient. Nothing refuses it before then.
- No file, section, slug, or edge changes. No rule changes severity.

## Open decisions (for ratification)

1. **Names.** `attended | unattended` (recommended). Alternatives: `paired |
   autonomous`, `collaborative | automated`.
2. **Key name.** `build:` (recommended). Alternative: `posture:`.
3. **Version.** `3.0.0` (recommended). Every v2.8 spec stays valid and no rule
   changes severity, which argues MINOR. But the founding premise, the default
   posture, the reading order, and the lifecycle's merge-first rule all
   change; a reader of the two canons is reading two different defaults. Both
   reviewers recommended MINOR on the grounds that the schema barely moves;
   the decider's call is whether the lifecycle change is the thing being
   versioned.
4. **Runner baseline.** SHOULD, mechanism left to the runner (recommended).
   Alternative: keep merge-first as a MUST for unattended only, which keeps two
   ratification stories alive in the canon.

## Cost, honestly

One new frontmatter key, one new advisory rule, one new prompt file and MCP
prompt entry, a reorder of the canon that moves roughly half its text into one
chapter without rewriting it, a split of the amendment section by posture, the
removal of four contradictions, and a runner-contract SHOULD. No rule changes
severity; no tool changes its output shape. The hand-maintained mirrors need
the same reorder and the same removals, which is the largest single piece of
work. The moving `@v3.0` tag is the one step that breaks consumers if missed.

What this does not do: build a runner, build `Specline diff`, change the spec
body, partition rule severity, or decide model routing or the corrections
harvester. Those stay exactly as open as they were.

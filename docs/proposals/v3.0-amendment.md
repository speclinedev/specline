# Canon v3.0 — amendment proposal (draft, for ratification)

**Status:** PROPOSAL — not yet ratified. Shaped 2026-09-05 from a run, not a
theory: the decider authoring specs for an attended builder and finding the
builder combative. Per `docs/research/findings.md` ("decide from runs, not
theory").

**Posture.** One structural change: the build posture becomes explicit, and
the canon is reordered so the attended spec is the whole default and the
autonomous machinery is an opt-in envelope. Every v2.8 spec stays valid.
Nothing is deleted from the methodology; the parts written for a runner move
behind a key so they stop loading for a builder that is not one.

---

## In plain terms (read this first)

Specline has two products fused in one canon. The first is the spec
discipline: one folder shape, intent and non-goals, a checkable definition of
done, open questions with a default, graduation into permanent knowledge. The
second is a runner contract: loop budgets, staleness, frozen checks, a
six-section status file with machine tokens, blast-radius routing, decider
budgets. The second was designed for an orchestrator that was never built, and
today every agent that reads the canon loads all of it.

The founding sentence of the canon says the builder is "a different agent,
never in the room, unable to ask what you meant." In the run that produced this
proposal the builder was in the room, and asked. When that premise is false,
everything derived from it is dead weight the builder still carries, and the
contract language it carries ("frozen relative to the implementer", "the
builder does not weaken the ruler", "handback", "quarantine") turns a partner
into a rules lawyer.

Three moves fix this without losing anything:

1. **A spec is attended unless it says otherwise.** No field to set, no
   question to answer. The spec body as written today is a complete attended
   spec. Marking a spec unattended is an explicit upgrade, and the checker
   tells you what the upgrade costs the moment you choose it.
2. **The autonomous machinery becomes the unattended envelope.** Same
   primitives, same rules, grouped, named, and only in force when the key is
   set. The canon describes the attended spec first as the whole thing;
   unattended is a later chapter.
3. **The builder gets a brief.** Shaping has a persona tuned for partnership.
   Building has none, so the builder reads the legal text. A `build` prompt
   gives the attended builder the same posture the planner already has: audit
   the spec, disagree out loud, propose in product terms, edit once agreed,
   then build.

Kept unchanged: the spec body, slug identity, graduation and archive,
integrity-only blocking, open questions with defaults, the three altitudes of
acceptance as *who certifies done*.

## C1 — Build posture: `build: attended | unattended`

**Change.** One new frontmatter key on `spec.md`:

```yaml
build: unattended     # OPTIONAL. attended | unattended. Absent means attended.
```

The key names the one variable that decides whether the autonomous machinery
is load-bearing: **can the builder reach the decider during the build.**

- **attended** (default, and the meaning of absence). A human, or an agent
  with the decider reachable, builds. The builder audits the spec, disagrees
  out loud, and edits the spec in the build branch once the decider agrees.
  The diff is the amendment record. No status schema, no budgets, no routing
  fields are required or checked. Mechanics stay sparse because the builder
  can ask.
- **unattended.** A fresh-context agent builds alone and the decider sees the
  result at QA. Marking a spec unattended is a promise: a builder that cannot
  ask anything has everything it needs. The unattended envelope (C2) is in
  force, the runner contract applies, and a mid-build contradiction parks the
  spec instead of improvising.

**Why absence means attended.** The decider does not reliably go through the
shape prompt; specs are drafted by an agent after a long conversation, from
the canon as read. Any mechanism that depends on a question being asked does
not reach that path. The format has to carry the decision. The cheap posture is
the default; the expensive one is a visible, additive, reversible upgrade.

**Set at shaping, confirmed at ratify.** The planner asks it early in product
terms ("will someone be around while this gets built, or does it run on its
own"), because it sets how much detail the spec carries. It is confirmed at
ratification because it is the same class of judgment as risk, and a spec can
be shaped attended and handed off later.

**The body does not fork.** Intent, Goal, Non-goals, Behavior, Business rules,
Assumptions, Critical files, Acceptance checks, Out of scope are identical in
both postures. Two specs of the same feature stay comparable and graduation
has one shape. Only the envelope differs.

**Failure mode.** A spec built unattended without the key set. Nothing in the
folder tells the runner it is unattended, so the envelope is not checked and
the builder may run without memory or a budget. Mitigation: a Specline-compliant
runner refuses a spec that lacks `build: unattended` (runner contract, C5).
The fence is on the runner, not the author.

## C2 — The unattended envelope

**Change.** The following, all existing in v2.8, are grouped as the
**unattended envelope** and required or checked only when
`build: unattended`:

| Surface | v2.8 status | v3.0 status |
|---|---|---|
| `blast_radius` | required at ratify (advisory warn) | envelope |
| `size` | declared build size (advisory) | envelope |
| `target_model` | optional | envelope |
| `loop_budget` | optional | envelope |
| `stale_after` | set on building/blocked | envelope |
| `status.md` schema (six sections, machine tokens) | required for autonomous builds | envelope; attended `status.md` is optional and free-form |
| Frozen provable checks (B5) | always | envelope; attended checks change by agreement in the build branch |
| Corrections promotion, `## Corrections` shape | required | envelope |
| Inner and outer loops, `review_rounds_before_human` | canon body | envelope chapter |
| Routing and cost estimation | canon body | envelope chapter |
| Agent-execution notes | canon body | envelope chapter |
| Runner contract | open questions | envelope chapter |
| Decider budget (B7), staleness (B4), coupling ceiling (B2) | tier 2 | envelope, tier 2 within it |

Nothing is removed from the methodology. Every primitive keeps its definition
and its rule; the change is *when it is in force* and *where in the canon it
sits*. An attended spec that carries envelope fields anyway is legal; they are
preserved and not checked.

**Why.** The primitives are valuable and still being explored. Deleting them
loses the thinking; leaving them in the default path loses the reader. The
envelope keeps both.

## C3 — The canon reads attended first

**Change.** The canon is reordered. The attended spec is described as the
whole thing: What this is, the Boundaries that survive without a runner (B1
One-Sitting, B3 Human Gate, B5 Falsifiable, B6 Intent), Roles, Repository
layout, IDs, Spec folder anatomy, the body, `open-questions.md`,
`relations.md`, Decomposition, Selective loading, Lifecycle, Enforcement,
Adoption. Then one chapter, **Unattended builds**, holding the envelope: the
remaining Boundaries (B2, B4, B7), the `status.md` schema, Promotion, the
build loop, Routing, Agent-execution notes, the runner contract.

The founding sentence changes. v2.8: "You shape a feature with one agent, and
a different agent builds it — fresh context, never in the room, unable to ask
what you meant." v3.0: "A spec carries the decision so that whoever builds it,
a person, an agent beside you, or an agent alone overnight, builds what you
meant. A spec is attended unless it says otherwise; marking it unattended is a
promise that a builder who cannot ask has everything it needs."

**`specline_spec` serves by posture.** The tool gains an argument,
`unattended: boolean` (default false). Default returns the attended canon; true
appends the Unattended chapter. The MCP resource and the agent brief instruct
the builder to pass true when any spec in scope carries `build: unattended`.
Without this the reorder is decoration: the agent still loads all of it.

**Why.** The canon's own B2 argument applies to the canon: irrelevant forced
loads degrade output. An agent drafting from memory of the canon lands on the
right default because the default is what it read first.

## C4 — Amendment is a normal move, attended

**Change.** Lifecycle, *Amendment (reshape) mechanics*, splits by posture.

- **Attended.** The builder finds a contradiction or a better cut, says so in
  product terms, and the decider agrees or not in the conversation. On
  agreement the builder edits `spec.md` in the build branch. The decider's
  approving merge of the implementation PR ratifies the amended contract with
  the code. Acceptance checks are part of the contract: the builder proposes a
  change to a check before changing it, never silently. No status flip, no
  separate spec PR, no re-ratification ceremony.
- **Unattended.** Unchanged from v2.8: flip to `blocked`, spec-amendment PR to
  the merge target, decider approval, resume. This is a handback because there
  is no conversation to have.

**Ratification, attended.** The decider's go is the ratification. The strongest
form is the approving merge of a spec PR to the merge target (v2.8, unchanged
and still recommended when a spec is shaped ahead of its build). Attended, the
spec and its build commonly land in one PR; there the decider's explicit
`status: building` flip in the build branch is the go, and the implementation
PR's approving merge is the record. Git still owns who and when.

**Contradiction fixed.** v2.6 removed `ratified_by` and `ratified_at` and made
the merge the record; the Lifecycle two-PR text, the amendment mechanics, and
`docs/conventions/specline-CLAUDE.md` still instruct setting them. v3.0 removes
every remaining instruction to set those fields. An agent given contradictory
rules gets defensive.

**Why.** v2.8's own instrumentation expects a mid-build revision rate of
10–40% and then models the normal path as a failure path. The builder in the
run behaved as if in a handback when it was in a conversation.

## C5 — The builder brief

**Change.** A second MCP prompt, `build`, served from `cli/prompts/builder.md`,
in the register of the v0.3 planner persona (one-line role, calm imperatives,
a clause of why on load-bearing rules, methodology backstage). Its posture, in
brief:

> You are building from a spec a product owner wrote or co-wrote. Read the
> whole folder. Audit it against the code before you write any: what it gets
> wrong, what it leaves out, what would be cheaper another way. Disagree out
> loud, in product terms. When the owner agrees, edit the spec in this branch;
> the diff is the record. Acceptance checks are the contract's definition of
> done: propose a change to one before you change it, never silently. Then
> build, and ground every claim of done in a tool result.

When the spec carries `build: unattended` the prompt instead loads the
Unattended chapter and the runner contract, and the posture is the v2.8 one:
frozen checks, status memory, escalate at a boundary.

`docs/conventions/specline-CLAUDE.md` gains one line: *a spec is attended
unless it says otherwise; marking it unattended means you are promising a
builder that cannot ask you anything has everything it needs.* And loses its
`ratified_by`/`ratified_at` instruction.

**Runner contract addition.** A Specline-compliant runner MUST refuse to start
an unattended build on a spec that does not carry `build: unattended`. This is
the fence for C1's failure mode and the only new MUST in the runner contract.

**Why.** The combative feel traced to three causes: no builder brief, amendment
modeled as an exception, and the ratification contradiction. C4 and C5 address
all three. The brief is the cheapest and the first to ship.

## Doctor rules — partition by posture

Integrity rules are unchanged and always fire: `STRUCT-MISSING-SPEC`,
`FRONTMATTER-UNPARSEABLE`, `FRONTMATTER-SLUG-MISMATCH`, `ENUM-INVALID`,
`RELATION-DANGLING`, `LINK-DANGLING`, `SLUG-DUPLICATE`, `KNOWLEDGE-HAS-STATUS`,
`ARCHIVE-EDITED`. `ENUM-INVALID` gains `build` (`attended|unattended`).

Advisory rules that fire in both postures (they are about the body, which does
not fork): `STRUCT-MISSING-RELATIONS`, `UNKNOWN-FRONTMATTER-KEY`,
`UNKNOWN-SECTION`, `RELATION-CROSS-REPO`, `RELATION-KILLED`, `GOAL-MISSING`,
`JUDGEABLE-NO-SECTION`, `CHECK-RUN-MALFORMED`, `PARENT-HAS-MECHANICS`,
`PARENT-NO-SCOPES`, `CANON-PIN-MISMATCH`, `OPEN-QUESTION-INCOMPLETE`,
`OPEN-QUESTION-OVERDUE`, `ARCHIVE-NO-ACCEPTANCE`.

Advisory rules that fire only when `build: unattended` (the envelope):
`STATUS-SCHEMA`, `CORRECTIONS-MALFORMED`, `LOOP-BUDGET-INVALID`,
`RATIFIED-NO-BLAST-RADIUS`, `RATIFIED-ACCEPTANCE-UNPARTITIONED`,
`SCOPE-EXCEEDS-SIZE`, and the tier-2 set `STALE-QUARANTINE`,
`DECIDER-OVER-BUDGET`, `COUPLING-CEILING`.

New rule:

| rule_id | fires when |
|---|---|
| `UNATTENDED-INCOMPLETE` | `build: unattended` and any envelope requirement is absent: `blast_radius`, `loop_budget`, `stale_after` once building, a `status.md` conforming to the schema. Advisory. This is the "distance to unattended-ready" report the author sees the moment they set the key. |

Author mode already reports missing required elements as
`distance_to_ratifiable`; `UNATTENDED-INCOMPLETE` is the same report for the
envelope.

## Migration — non-breaking for specs

- A v2.8 spec without `build:` is attended. Its envelope fields, if any, are
  preserved and not checked. It validates.
- A v2.8 spec that was being built by a runner adds `build: unattended` and
  validates exactly as before; every envelope rule it passed it still passes.
- No file is renamed, no section is renamed, no slug or edge changes.
- The MAJOR bump is for the reading contract and the default posture, not for
  spec validity. See open decision 4.

## Open decisions (for ratification)

1. **Names.** `attended | unattended` (recommended: they name the fact, not a
   role, and `unattended` reads as the promise it is). Alternatives considered:
   `paired | autonomous`, `collaborative | automated`.
2. **Key name.** `build:` (recommended; short, and the value reads as a
   sentence: "build: unattended"). Alternative: `posture:`.
3. **What `tier` still means.** Recommended: tier stays a repo-level
   declaration for now, with Tier 2 defined as "this repo runs unattended
   builds and wants the parallel-work governance." Revisit whether the presence
   of any `build: unattended` spec can replace the declaration once there is a
   run to decide from. Do not add a third knob.
4. **Version.** `3.0.0` (recommended). Every v2.8 spec stays valid, which would
   argue MINOR, but the canon's founding premise, default posture, reading
   order, and amendment path all change, and the tool's `specline_spec`
   default output changes. A reader of the two canons is reading two different
   defaults. That is a MAJOR reading-contract change even though it is a MINOR
   schema change.
5. **`specline_spec` default.** Attended-only by default (recommended), with
   the brief instructing the builder to request the chapter when a spec in
   scope carries the key. Alternative: always serve both, which restores the
   load this proposal exists to remove.
6. **Attended ratification record.** The `status: building` flip by the decider
   in the build branch, with the implementation PR merge as the record
   (recommended, C4). Alternative: require a spec PR ahead of every build,
   which is the v2.8 rule and the ceremony the run found unnecessary.

---

## Cost, honestly

One new frontmatter key and one new advisory rule. A reorder of the canon that
moves roughly half its text into one chapter without rewriting it. One new
prompt file and one MCP prompt. One argument on `specline_spec`. A split of the
amendment section by posture and the removal of a contradiction. The
hand-maintained mirrors (handbook, site reference pages, README) need the same
reorder, which is the largest single piece of work and the one most likely to
drift; it should land in the same release as the canon.

What this does not do: it does not delete a primitive, build a runner, change
the spec body, or decide anything about model routing or the corrections
harvester. Those stay exactly as open as they were.
